> **The problem:** every new backend project restarts the same arguments from
> zero — how routes should be structured, how errors should look, how to test
> any of it without babysitting a live server.
>
> **The fix:** decide it once, document it, test it properly, and reuse it.

![VitePress docs homepage — hero section with "Get Started"/"Architecture" actions and the Batteries Included / TypeScript First / Production Ready feature cards](/server-template/server_docs_home.png)

## Why I Built This

Going into this project I could have picked any backend stack. I chose Fastify
specifically — over Express — because of its numbers and its design: a schema-driven
core built for high throughput, and a plugin/encapsulation model that looked like it
would actually hold up as an app grows, rather than turning into a pile of
middleware. It was the framework that looked like the best combination of
performance and design decisions for what I wanted to build going forward.

Having made that choice, I didn't want to learn it by piecing things together from
scattered blog posts. I read _Accelerating Server-Side Development with Fastify_
(Packt) cover to cover — written by Fastify's own core contributors, with real,
runnable code examples throughout. But reading isn't the same as knowing. So instead
of a tutorial project I'd throw away, I built something meant to
be reused: an opinionated backend template I could drop into the next client project
on day one — routing, validation, error handling, logging, auth-ready plugins, docs,
and a test setup already wired together and already agreed upon, so the first commit
on a new project is a feature, not scaffolding.

The constraint I set for myself going in: **it has to stay easy for someone else (or
future me) to open any single piece and change it without understanding the whole
system first.** That constraint is what drove most of the architecture decisions
below — grouping by domain, explicit dependencies between modules, and documenting
the "why" alongside the code instead of leaving it as tribal knowledge.

## What It Is

A production-shaped Fastify 5 + TypeScript template — not a toy example, a real
foundation. Request validation, a consistent API response envelope, centralized
error handling, structured logging with request-id tracing, rate limiting, CORS,
security headers, cookie handling, file uploads, Cloudinary integration, a Prisma +
PostgreSQL data layer, auto-generated Swagger/OpenAPI docs, and a full internal
documentation site — **all pre-wired, pre-tested, and pre-documented** before a
single feature of the actual product gets written.

|            |                                                                              |
| ---------- | ---------------------------------------------------------------------------- |
| **Role**   | Sole developer                                                               |
| **Type**   | Personal / internal tooling                                                  |
| **Stack**  | Fastify 5, TypeScript, TypeBox, Prisma, PostgreSQL, Vitest, VitePress        |
| **Output** | Reusable backend template, ~40 source files, full test suite, full docs site |

## Tech Stack & Why Each Piece Is There

- **Fastify** — chosen over Express for its throughput (schema-based serialization
  and validation instead of general-purpose middleware chains) and for its
  plugin/encapsulation model, which looked like the better long-term design for
  something meant to scale across features and teams. Learned properly via
  _Accelerating Server-Side Development with Fastify_ (Packt), written by Fastify's
  own core contributors.
- **TypeScript, strict** — `strictTypeChecked` + `stylisticTypeChecked` ESLint
  configs, plus `eslint-plugin-unicorn` and a custom `naming-convention` rule set.
- **TypeBox + `@fastify/type-provider-typebox`** — one schema definition drives
  runtime validation, the compiled TypeScript type, and the OpenAPI docs. No writing
  the same shape three times.
- **Prisma + PostgreSQL** — typed data access, migrations, and a real (not mocked)
  database in tests and CI.
- **Vitest** — unit and integration tests, run against the same app the server
  actually boots (see below).
- **VitePress** — the template ships its own documentation site, versioned in the
  same repo as the code it documents.
- **Husky + lint-staged + commitlint** — enforced Conventional Commits and
  format/lint-on-commit, plus type-check/lint/test on pre-push.
- **pnpm workspace, `tsx`, `tsc-alias`** — fast dev loop with path aliases (`@/`)
  that still resolve correctly after compilation.

## Project Setup — What `package.json` Actually Does

Rather than one `npm start`, the scripts are grouped by concern, each pointed at the
right environment file automatically:

```json
"scripts": {
  "dev": "tsx watch --env-file=.env --clear-screen=false src/bin/server.ts",
  "build": "pnpm clean && tsc && tsc-alias",
  "start": "node dist/bin/server.js",
  "typecheck": "tsc --noEmit",
  "test": "vitest run",
  "test:coverage": "vitest run --coverage",
  "docs:dev": "vitepress dev docs",
  "db:dev": "prisma migrate dev",
  "db:deploy": "prisma migrate deploy"
}
```

- `dev` loads `.env` and watches with `tsx` — no separate compile step locally.
- `test*` scripts load `.env.test` instead (wired through `vitest.config.js`), so
  tests never touch development data.
- `start` deliberately loads **no** `.env` file — production config is expected to
  come from real environment injection (container secrets, platform config), not a
  committed file. This is spelled out explicitly in the docs site, not left implicit.
- `db:*` scripts are just named Prisma commands (`format`, `gen`, `studio`, `dev`,
  `deploy`, `status`) — one place to remember, instead of everyone running raw
  `pnpm prisma ...` differently.

## Architecture: Functional Composition Over Fastify Plugins

There's no DI container and almost no classes in this codebase (the only two are
`ApiError`/`AppError`, and those exist purely because they need to extend `Error`).
Everything else — services, plugins, route registration — is a **plain async
function**, composed using Fastify's own plugin and encapsulation system. That was a
deliberate choice: Fastify already gives you a scoping and dependency mechanism, and
reaching for a class-based DI framework on top of it would just be two competing
systems solving the same problem.

Each domain is split into three kinds of files:

```txt
routes/api/v1/examples/todos/
├── handlers/
│   ├── create-todo.handler.ts   # one function per endpoint
│   └── list-todos.handler.ts
├── todos.routes.ts              # registers the handlers, declares its dependencies
└── todos.module.ts              # registers the service, then the routes
```

`todos.routes.ts` doesn't just register handlers — it **declares what it needs** and
lets Fastify enforce it at boot:

```ts
export const todosRoutesPlugin = fastifyPlugin(todosRoutes, {
  encapsulate: true,
  name: 'todosRoutes',
  dependencies: ['todosService'], // app refuses to start if this isn't registered first
});
```

Services follow the same shape — a loader function that decorates the Fastify
instance, wrapped in `fastify-plugin` so the decoration escapes its own encapsulation
boundary but nothing else does:

```ts
app.decorate('service', {
  ...app.service,
  todos: {
    async getTodos(options) {
      /* ... */
    },
    async createTodo(options) {
      /* ... */
    },
  },
});
```

The payoff of this structure is exactly the constraint I set at the start: any domain
folder (`todos/`, or a new `orders/` folder tomorrow) is **self-contained** — its own
handlers, its own service, its own explicit dependency line — so someone can open just
that folder, understand it, and **change it without tracing the rest of the app**. New
domains are added by copying this shape, not by learning a framework-specific
convention buried in a base class.

## Validation & the API Contract, From One Schema

Every request and response is defined once, in TypeBox, next to the handler that
uses it:

```ts
const BODY_SCHEMA = Type.Object(
  {
    title: Type.String({ description: '...', examples: ['Implement todos endpoints'] }),
    description: Type.Optional(Type.String()),
  },
  { additionalProperties: false },
);

const RESPONSE_DATA_SCHEMA = Type.Null();
type ResponseData = Static<typeof RESPONSE_DATA_SCHEMA>;
const RESPONSE_SCHEMA = createApiResponseSchema(RESPONSE_DATA_SCHEMA);
```

That one `BODY_SCHEMA`/`RESPONSE_SCHEMA` pair does three jobs at once: Fastify
validates the incoming request and outgoing response against it at runtime, `Static<>`
derives the exact TypeScript type for the handler body, and the same schema feeds
Swagger/OpenAPI generation — so the API docs can never silently drift from what the
server actually accepts and returns.

Every successful response is also wrapped in the same envelope
(`generateApiResponse`), and every error response goes through the same shape too —
so a frontend consuming this API only ever has to handle one response contract:

```json
{
  "success": true,
  "data": { "...": "..." },
  "message": "Todos fetched successfully",
  "meta": { "requestId": "req-1", "timeStamp": "2026-08-21T10:00:00.000Z" }
}
```

The same Scalar/OpenAPI setup — and the same response envelope — carried
forward into later projects built on this template. Below, an `Admin register
user` endpoint from a later e-commerce backend using this exact pattern (same
`success` / `data` / `meta.requestId` / `meta.timeStamp` shape), followed by a
live request run against server-template itself, where the response matches
the envelope shown above field-for-field:

## Centralized Error Handling

Routes never format an error response themselves — they either `throw apiError({...})`
for an expected, user-facing error, or let unexpected errors bubble up. A single
global handler (`registerErrorHandler`) is responsible for turning both into the same
response shape, logging the underlying error either way, and deciding — based on
error type, Fastify's built-in validation error codes, or status code — whether to
expose the real message or fall back to a generic one. Stack traces are only ever
included in the response when `APP_ENV=development`, never in production.

A closed set of error codes (`ERROR_CODES`, e.g. `USER.NOT_FOUND`,
`AUTH.INVALID_TOKEN`) means error identification is a stable string a frontend or a
log query can match on, not a parsed English sentence.

## The Core Decision: Testing the Whole App Without Starting a Server

This was the main technical problem I wanted to solve, not just accept as "how
Fastify testing works."

The trick is a one-line architectural split in `src/app.ts`:

```ts
async function buildApp(options) {
  const app = fastify(options.serverOptions ?? {}).withTypeProvider<TypeBoxTypeProvider>();

  app.decorate('secrets', options.environmentConfig);
  await app.register(externalModulePlugin);
  registerErrorHandler(app);
  registerNotFoundHandler(app);
  await app.register(routesModulePlugin, { prefix: '/' });

  return app; // note: no app.listen() here
}
```

`buildApp()` builds the **entire** application — every plugin, every route, every
error handler, fully configured — and stops. It never opens a socket. `app.listen()`
happens in exactly one place in the whole codebase: `src/bin/server.ts`, the actual
production entrypoint.

That split means the test suite can build **the identical object graph the
production server runs — minus the network listener**:

```ts
// test/helper.ts
export async function buildTestApp(options = {}) {
  const environmentConfig = loadEnvironmentConfig(options.environmentSchemaOptions);
  const { serverOptions } = getFastifyServerConfig({ environmentConfig });

  const app = await buildApp({ environmentConfig, serverOptions, plugins: options.plugins });
  await app.ready();

  return app;
}
```

Tests then use Fastify's built-in `app.inject()` — a real, in-process HTTP round trip
(routing, TypeBox validation, serialization, the actual global error handler) with no
socket, no port, and no external HTTP client:

```ts
const app = await buildTestApp();

const response = await app.inject({
  method: 'POST',
  url: '/api/v1/examples/todos',
  body: { title: 'Buy milk' },
});

expect(response.statusCode).toBe(201);
```

A few things fall out of this for free:

- **No port collisions, no flaky "address in use" failures in CI**, since nothing
  ever binds to a port during tests.
- **`buildTestApp()` accepts overrides** — a test can spin up the exact same app with
  a tweaked env var (`rate-limit.test.ts` sets `RATE_LIMIT_MAX: 5` to test the limiter
  in 6 requests instead of 101) or a narrower plugin set (`todos-service.test.ts`
  builds the app with _only_ `todosServicePlugin` registered, to test the service
  layer in isolation from the HTTP layer entirely).
- **The database itself is not mocked.** Tests run against a real PostgreSQL instance
  via Prisma (`.env.test` locally, an ephemeral `postgres:17.5` service container in
  CI). So this isn't unit testing with everything faked out — it's full integration
  testing of the real request pipeline, with only the network layer removed. That's
  a deliberate trade-off: it costs a running Postgres instance, but in return the
  tests catch schema and query bugs that a mocked Prisma client never would.
- Small, pure pieces of logic (`loadEnvironmentConfig`, error-code/message
  resolvers, `getTimestamp`) are tested directly as functions with no `app` at all —
  they don't need Fastify in the loop because they were written as functions with no
  side effects in the first place.

## Documentation Is Part of the Template, Not an Afterthought

A template only pays off if someone else (or future me, six months later) can extend
it without re-deriving the conventions from scratch. So the repo ships its own
VitePress documentation site (`pnpm docs:dev`) covering folder structure, routing
conventions, the service pattern, the plugin pattern, validation, error handling,
environment-variable behavior per script, every `package.json` script, naming
conventions, and what each git hook enforces. It's versioned in the same repo as the
code, so **the docs and the code can't drift apart** the way a wiki page tends to.

![Docs sidebar navigation (Getting Started, Project Architecture, Code Standards & Automation) alongside the Installation Guide page](/server-template/server_docs_installation.png)

The auto-generated API reference is separate from this — Swagger/OpenAPI docs are
generated from the same TypeBox schemas the routes validate against, served at
`/docs` in development only (never in production).

## Quality Gates, Enforced Before Code Ever Reaches CI

- **`pre-commit`** — `lint-staged` runs Prettier and ESLint `--fix` on staged files,
  and formats `prisma/schema.prisma`.
- **`commit-msg`** — `commitlint` rejects any commit message that doesn't follow
  Conventional Commits (`feat(scope): ...`, `fix(scope): ...`, etc.) — the whole
  commit history of this project follows that format as a result.
- **`pre-push`** — full `tsc --noEmit`, `eslint .`, and `vitest run` before code
  leaves the machine.
- **CI (GitHub Actions)** — mirrors the same three checks (lint, typecheck, test)
  against a real ephemeral Postgres service container, so CI is checking the same
  thing the pre-push hook already checked, just without trusting the local machine.

## What's Intentionally Not Built Yet

Tracked openly in the repo's own `TODO.md` rather than hidden:

- A metrics endpoint
- An example auth flow (the plugins — cookies, rate-limiting — are ready for it, the
  flow itself isn't wired up yet)
- Docker support (exists on a separate `feat/docker` branch, not yet merged)
- A CD (deploy) GitHub Actions workflow
- Log rotation / centralization guidance for production hosting
- A chosen license

None of these are missing by oversight — they're staged. The five phases in
`TODO.md` (bootstrapping → security/standards → core dev environment → app features →
deployment/observability) were worked through roughly in that order, and the commit
history follows the same phases.

## Why This Mattered

This wasn't built to solve one client's problem — it was built so the _next_ backend
project doesn't start from zero. Routing conventions, validation, error handling,
logging, and a real test setup are **decided once, documented once, and reused every
time after**. The part I'm most glad I got right: a test suite that runs the actual
production wiring — not a simplified stand-in for it — while never needing a real
running server to do it.
