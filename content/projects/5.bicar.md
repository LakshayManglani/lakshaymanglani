> **The ask:** BICAR — the Bombay Institute for Critical Analysis and
> Research — wanted to edit their own website: courses, faculty profiles,
> talks, upcoming programs, all of it, without needing a developer for every
> content change.
>
> **The catch:** their site wasn't a blog. Courses have dates and
> instructors, faculty have bios and photos, talks have their own type
> system, programs run on a schedule. None of that exists as a concept in a
> generic rich-text field.

## Why I Built This

BICAR is a real, active para-academy — a non-profit research and teaching
institute based in Bombay, working across critical philosophy, visual
culture, and the humanities. Their site needed to publish genuinely
different _kinds_ of content — courses, programs, talks, faculty, upcoming
offerings — each with its own shape, and they needed to be able to publish
it themselves.

![BICAR's live homepage — the institute's About text and faculty People section, with an Edit button visible top-right only because I'm logged in](/bicar/bicar-live-page.png)

A generic CMS form (title field, markdown textarea) would have technically
let them publish text. It wouldn't have given a course its start/end dates
and instructor, or a faculty member their photo and bio, as structured
things — just more undifferentiated text. What they actually needed was the
real page, editable in place, where every content type was a proper,
structured unit. So before writing the real thing, I researched how block
editors are actually built — this was the first project where I designed
that kind of system myself, from the ground up.

This is one of my earliest client projects — built in late 2024, before
either Server Template or Kathika.

## What I Explored First

`package.json` still has the evidence: `@blocknote/core`, `@blocknote/react`,
and `@blocknote/shadcn` sit right alongside `slate`, `slate-react`, and
`slate-history`. I evaluated BlockNote — a pre-built block-editor framework
— by actually building with it (`components/BlockNoteEditor/Editor.tsx`),
not just reading its docs.

BlockNote is genuinely good at what it's built for: paragraphs, headings,
lists, generic content blocks. What it doesn't give you for free is a
**course card with a start date** or a **faculty profile with a bio field**
as an editable block — those are exactly this client's content, and no
block-editor framework ships them out of the box. Adapting BlockNote to
support fully custom, application-specific block types would have meant
fighting its abstractions as much as using them.

Slate is lower-level by design — it gives you the document model and
leaves rendering entirely to you. That's more work up front, but it means
each of BICAR's real content types could be a first-class node from day
one, rendered by my own components, with no framework opinion in the way.
I built the real editor on Slate; the BlockNote experiment is still sitting
in the repo, unused by anything, next to the version that shipped.

## The Editor

The shape that came out of this research is the same shape you'll find
(more refined) in Kathika: a Slate editor instance wrapped in `withReact` +
`withHistory`, a `renderElement`/`renderLeaf` pair that dispatches on a
node's `type` to my own React components, and a single `readOnly` flag —
driven by whether the visitor is logged in as an admin — that decides
whether the exact same rendered page is a live site or a live editor:

```tsx
const editor = useMemo(() => withInlines(withHistory(withReact(createEditor()))), []);

return (
  <Slate editor={editor} initialValue={parsedContent} onChange={handleChange}>
    {readonly ? null : <Toolbar />}
    <Editable
      readOnly={readonly}
      renderElement={(props) => <Element {...props} />}
      renderLeaf={(props) => <Leaf {...props} />}
      placeholder="Type '/' for commands"
    />
  </Slate>
);
```

There's no separate "editor view" and "live view" — `PageEditor` renders
once, and that one `readonly` flag decides whether `Editable` accepts input
at all:

![The same page, editable — clicking Edit swaps in a floating formatting toolbar (paragraph type, bold/italic/underline, color, alignment, font size, link) and turns the top-right button into Preview](/bicar/bicar-edit-toggle.png)

Content insertion runs through a searchable element picker — six custom
block types shipped this way: Accordion, Carousel, Image, TwoColumn,
UpcomingCard, and WriteCard, on top of the base text/heading nodes:

![The element picker mid-search, plus the "module" system below it — bordered containers with explicit Add module / Remove module controls, grouping repeating cards like the blue "Write: Office Hours" card and the Style/Argument/Logic trio](/bicar/bicar-module-elements.png)

That screenshot also shows the other half of the editing model: not
everything is free-flowing rich text. Repeating card grids (the colored
"Core Modules" section, the office-hours card) are wrapped in an explicit
module container with its own Add/Remove controls — a more structured,
form-like editing pattern layered on top of the free-form Slate content,
for the content that's genuinely list-shaped rather than prose-shaped.

## Six Kinds of Pages, Managed From One Sidebar

BICAR's content isn't one page type — it's courses, programs, talks,
faculty profiles, and upcoming offerings, each with its own required fields
(a course needs dates and an instructor; a talk needs a type; faculty need
a photo and bio). A logged-in admin manages all of it — and the site's whole
navigation structure — from one page-tree sidebar:

![The page-management sidebar — every top-level page (Home, Para-academy, Upcoming, Past, Write, Curate, Faculty, Sorkin-price, Edit, Contact, Text-editor, About), each expandable, letting the admin restructure the site's own navigation](/bicar/bicar-page-sidebar.png)

Each of those content types renders as its own page — including detail
pages that carry structured metadata a plain rich-text document can't:

![A course's own page: title, date range, instructor, and rich body content with an inset captioned image — structured fields plus free-form content on the same document](/bicar/bicar-course-detail.png)

![The "Past" listing, with tabs for Courses / Programs / Talks — each card pulling its thumbnail and description straight from that document's structured fields](/bicar/bicar-past-listing.png)

## The Backend: One Schema, Six Shapes

The API (Express + MongoDB via Mongoose, JWT-in-cookie auth, Cloudinary for
image storage) models this with **Mongoose discriminators** — one base
`Document` schema shared by every page (title, url, `isPublished`, the
Slate `content` JSON, an optional parent for nesting), with each content
type extending it with only the fields it actually needs:

```js
const BaseDocumentSchema = new mongoose.Schema(
  {
    title: { type: String, required: true },
    url: { type: String, required: true },
    content: { type: String, required: true },
    type: {
      type: String,
      required: true,
      enum: ['normal', 'course', 'program', 'talk', 'faculty', 'upcoming'],
    },
    // ...isPublished, parentDocument, bgColor, bgImage
  },
  { discriminatorKey: 'type', timestamps: true },
);

BaseDocumentSchema.discriminator(
  'course',
  new mongoose.Schema({
    thumbnail: { type: mongoose.Schema.Types.ObjectId, ref: 'Image', required: true },
    author: { type: String, required: true },
    date: { type: Date, required: true },
  }),
);

BaseDocumentSchema.discriminator(
  'faculty',
  new mongoose.Schema({
    profilePicture: { type: mongoose.Schema.Types.ObjectId, ref: 'Image', required: true },
    name: { type: String, required: true },
    bio: { type: String, required: true },
  }),
);
// ...program, talk, upcoming follow the same pattern
```

One collection, one query path, six real shapes — a course is guaranteed to
have a date and an author at the schema level, a faculty page is guaranteed
a bio and a photo, and the frontend's `NormalDocument`/type-filtering logic
maps directly onto this without either side inventing its own parallel
notion of "what a course is."

The rest of the API is a conventional, cleanly organized Express service:
`controllers/<domain>/handlers/*.js` + `routes/` + `models/` +
`validations/` per domain (auth, documents, images, fonts, subscriber,
query — the last one backing the contact form), a JWT-in-httpOnly-cookie
auth middleware with role-based route guards, an `asyncHandler` wrapper so
controllers never hand-roll try/catch, and Cloudinary behind a small
service module for image uploads via Multer.

## This Became Kathika

A second client came to us with essentially the same underlying need:
content editable in place, not through a detached admin form. Rather than
re-run this research and rebuild the same architecture from zero, I
directed the reuse of this exact pattern — Slate editor, typed element
dispatch, the single `readOnly` toggle, a documents API shaped around
distinct content types — for that project, with a collaborator (Chirag
Wadhwani, who worked with me on this project too) doing the bulk of the
hands-on adaptation and new block types under that direction. I focused my
own time there on hardening what shipped here, most notably an
offline-resilience layer this version didn't have.

The full story of that reuse — what changed, what I built directly, and
what "directing" actually meant in practice — is in the
[Kathika case study](/projects/kathika).

## Why This Mattered

The pressure test here wasn't "can I integrate a rich-text library" — it
was "can I look at a client's actual, specific content — six different page
shapes, structured metadata, a real editing workflow for non-technical
staff — and design both the document model and the editor around what it
actually is, not around what a generic CMS assumes it should be." This was
one of the first times I did that end to end, frontend and backend, and the
architecture held up well enough that reusing it — instead of rebuilding it
— was the obvious call the next time the same problem showed up.
