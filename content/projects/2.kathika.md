> The second time a client needed "edit the real page, not an admin form,"
> we didn't start from zero. We already had the architecture — the question
> was how to reuse it well, and what to add.

## Where This Starts

Kathika is a museum and cultural centre in Old Delhi — two restored
19th-century havelis, with a public site covering their culture and
heritage collection, events and collaborations, team, and a trust page.
Completely different domain from the last client this architecture served
(a Bombay research institute), which is exactly the point: the same editor
pattern held up across two unrelated clients.

![The public-facing Kathika site — no editor chrome, just the site, when not logged in as admin](/kathika/kathika-public-view.png)

Kathika's editor is a direct descendant of the one I researched and built
from scratch for that earlier client, [Bicar](/projects/bicar) — same core
idea: a Slate document tree, a `renderElement` dispatch to typed React
components, one `readOnly` flag deciding whether the live page is also the
live editor. If you want the story of why that architecture is shaped the
way it is — the block-editor frameworks I evaluated, why I built on Slate
instead — that's in the Bicar case study, not repeated here.

This one is about what changed the second time: how that pattern got reused
for a new client, what got upgraded in the process, and what I actually
built on top of it myself.

## My Role, Honestly

I wasn't the primary hands-on implementer here, and the commit history shows
it plainly — of this repo's commits, the majority are a collaborator's,
Chirag Wadhwani, not mine. That's deliberate, not a gap: I'd already done
the research and built the architecture once on Bicar. For a second client
with the same underlying need, the efficient move was to hand Chirag that
proven pattern — "read this, adapt it, extend it for this client" — rather
than have both of us re-derive it.

What I did do directly: set the technical direction and reviewed the work
(a chunk of my commits here are merges), and I built the one piece of this
project that didn't exist in Bicar at all — the offline-resilience layer
below, which is entirely mine.

## What Actually Grew From Bicar to Here

The core loop is unchanged — Slate tree, typed elements, one `readOnly`
switch — but a few things matured a lot in the reuse, visibly so in how the
editor itself looks and behaves:

![Logged in as admin: a floating action bar appears — Edit, an "Archived" toggle, and delete — directly on the live page, no separate screen](/kathika/kathika-admin-toolbar.png)

That "Archived" switch is one click, wired straight to the document's
publish state:

```tsx
<Switch
  id="publish"
  checked={!selectedDocument.isPublished}
  onCheckedChange={handlePublish}
/>
<Label htmlFor="publish">Archived</Label>
```

`handlePublish` just flips `isPublished` and `PATCH`es it to the API. Bicar
never had this — publishing there was implicit. Here, an admin can draft a
page, leave it archived while it's not ready, and flip it live the moment
it is, without touching a deploy.

The editing surface itself moved from Bicar's inline toolbar-in-a-row to a
proper sidebar panel — a searchable element picker that shows every
insertable type and marks which one is currently selected:

![The element picker open on a selected Hero Section — a searchable dropdown listing every block type (Dialog, Email Subscribe, Heading 1–3, Image, Image Gallery...) with a checkmark against the current one](/kathika/kathika-element-picker.png)

— and a contextual options panel that changes completely depending on what
you've selected, not a fixed properties form:

![A Container selected: Leaf formatting (bold/italic/underline/quote, text color, font size) plus contextual Extra Options — insert-paragraph, container name, min/max dimensions, background — around a real image-gallery layout from the site's collection](/kathika/kathika-element-options.png)

Beyond the editor itself:

- **~20 block types instead of 6** — `hero-section`, `about-section`,
  `article-section`, `two-column`, `card`, `image-grid`, `image-gallery`,
  `brand-carousel`, `team-members`, `events`, `map`, dialogs, and more, each
  with its own options panel like the one above — a real property-inspector
  system, not just insertable blocks.
- **A two-tier content model** — the free-form Slate tree handles arbitrary
  page layout, while a separate tabbed `/admin` dashboard handles
  structured, list-shaped content that feeds into it (covered below). Bicar
  didn't need this split; Kathika's client did.
- **Proper domain-scoped state** — Bicar's `document-provider.tsx` /
  `auth-provider.tsx` were single flat files; here every domain (Document,
  Editor, Image, Auth, Event, TeamMembers, Brand, Article, Subscriber,
  Fonts) gets its own `context/<domain>/{Provider,types}.tsx`.

## Add It Once, It's Live Everywhere

The `/admin` dashboard handles the content that's genuinely list-shaped
rather than page-shaped — team members, events, brand logos, articles,
subscribers, images — each with its own tab, an add form, and a live list
right below it that updates the moment you submit:

![Adding a team member — Title, Post, and an image picker searching the existing media library — with the current team list (Atul Khanna, Ashna Khanna, Lovely Bhadra, Javeria Tanveer) shown live below the form](/kathika/kathika-admin-team.png)

![Adding an event — Title, Form URL, Start/End Date pickers, Event Banner — with three existing events already listed underneath, each deletable in place](/kathika/kathika-admin-events.png)

Submit that form and the new team member or event is in the same
`TeamMembersProvider`/`EventProvider` state the public "Our Team" and
"Events & Collaborations" pages already render from — there's no separate
publish step, no rebuild, no second place to keep in sync. That's the same
principle as the editor's single `readOnly` toggle, applied to structured
content instead of free-form pages: one source of truth, immediately
reflected wherever it's rendered.

## What I Built Directly: Staying Up When the Backend Doesn't

This is mine, and it's the part of Kathika that doesn't exist anywhere in
Bicar. The brief I set for myself: **it's better to show slightly stale
content than a blank page or a spinner**, so the site should survive its own
backend being down.

It works in two parts. At build time, a script
(`src/lib/loadServerData.ts`) hits the live API for every content type —
documents, images, events, team members, brands, articles — and bakes the
result into static JSON files (`public/api/*.json`) that ship as part of the
build:

```ts
const fetchDocuments = async () => {
  const { data } = await apiClient.get('documents');
  await storeTextInFile('./public/api/documents.json', JSON.stringify(data.data.documents));
};
```

Then at runtime, every fetch tries the live API first, with a 5-second
timeout, and falls back to that baked-in static snapshot on any failure —
timeout, network error, backend down entirely:

```ts
try {
  const { data } = await withTimeout(apiClient.get('documents'), 5000);
  documentDispatch({ type: 'SET_DOCUMENTS', payload: data.data.documents });
} catch (error) {
  const data = await fetch('/api/documents.json');
  documentDispatch({ type: 'SET_DOCUMENTS', payload: await data.json() });
}
```

No service worker, no offline-caching library — just a build step and a
try/catch. The tradeoff is honest: visitors can see content that's up to
one build old if the API is down, instead of the actual current state. For
a marketing/content site, that's the right tradeoff — stale-but-present
beats correct-but-blank every time the backend hiccups.

## Why This Mattered

The interesting decision on this project wasn't a line of code — it was
recognizing that the second client's problem was the _same_ problem, and
that directing a proven architecture's reuse was worth more than either of
us re-solving it independently. Reuse didn't mean "unchanged," either — the
publish toggle, the sidebar editor, the two-tier content model, and the
admin dashboard's add-once-reflects-everywhere pattern all grew out of what
this client actually needed. And the one piece I did build myself came from
taking that "reuse, don't rebuild" instinct one step further: the
resilience layer isn't part of the original architecture either — it's what
I added once I had the bandwidth, because a CMS that goes fully dark the
moment its API hiccups was a gap worth closing.
