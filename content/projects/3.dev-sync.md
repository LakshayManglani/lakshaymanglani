> **The idea:** a social platform for frontend developers — share components,
> projects, and articles, "stay synced with frontend trends."
>
> **The honest status:** unfinished. Paused for a long stretch while client
> work took priority, and never fully resumed. This case study is about what
> got built anyway, and what building it taught me.

## Why I Built This

This was a personal project, not client work, and the goal was learning as
much as shipping. I wanted to actually understand microservices —
not by reading about them, but by designing and running a real one — and I
wanted to get properly good at UI design instead of working from other
people's design systems. Dev Sync was the vehicle for both at once: a
frontend-developer-focused social platform, planned as a full microservices
backend from day one.

> **At a glance:** design work started Oct 2024, code from Nov 2024, both
> repos' last commits Feb 2025 · 3 of roughly 20 planned services fully
> working end to end, a 4th scaffolded · a full custom Figma design system
> built before any component was coded.

## The Architecture: What I Aimed For vs. What I Shipped

The full plan — shared on LinkedIn as I was designing it — was ambitious:
an API gateway and load balancer in front of roughly twenty services (auth,
user, post, follow, like, search, rating, review, comment, forum,
notification, feeds, chat, media, email, and more), Kafka and Redis for
messaging and caching, Postgres and MongoDB for storage, and a full
Grafana/Prometheus/Loki monitoring stack:

![The full planned architecture — API gateway and load balancer in front of ~20 core services, Kafka and Redis alongside them, Postgres/MongoDB storage, and a Grafana/Prometheus/Loki monitoring stack](/dev-sync/dev-sync-architecture-vision.png)

What's actually running is a real slice of that, not a mock of it: an API
gateway in front of **auth-service**, **email-service**, and
**user-service**, each its own repo with its own Dockerfile, talking to
each other over Kafka instead of direct calls. A fifth,
**connection-service**, exists at a different stage — a correctly-designed
`Follow` schema (compound unique index on follower/following pairs) with
no routes wired up yet, which is an honest snapshot of exactly where the
pause landed: some pieces fully working end to end, others scaffolded and
waiting.

![The architecture that actually shipped — API gateway, load balancer, Auth and Email services with real Kafka pub/sub between them, Postgres for AuthDB, monitoring stack alongside](/dev-sync/dev-sync-architecture-built.jpeg)

### Three Services, One Signup — a Real Event Choreography

This isn't one pub/sub link between two services, it's a full flow: submit
the registration form, and `auth-service` doesn't create an account yet —
it creates a `TempUser` and publishes to Kafka's `email` topic:

```js
const tempUser = await TempUser.create({ email, token, givenName, familyName, username, password });

await kafkaProducer.getInstance().send({
  topic: 'email',
  messages: [
    {
      partition: 0,
      value: JSON.stringify({
        type: 'auth/verification',
        data: { username, verificationLink: `${env.VERIFICATION_LINK}/${token}`, to: email },
      }),
    },
  ],
});
```

`email-service` consumes that, renders the `auth/verification` template,
and sends the real email (more on exactly how, below). Only when the user
clicks the link does `auth-service` create the permanent `AuthUser` — and
publish _again_, this time to a `user` topic:

```js
await user.save();
await kafkaProducer.getInstance().send({
  topic: 'user',
  messages: [{ value: JSON.stringify({
    eventType: 'createUser',
    data: { authUserId: user._id, username: user.username, email: user.email, ... },
  }) }],
});
```

`user-service` consumes _that_ event and creates the corresponding profile
document in its own database — a database `auth-service` never touches.
Username changes and email updates follow the identical pattern
(`updateUsername`/`updateEmail` events, consumed by `user-service` to keep
its own copy in sync). That's three independently deployable services,
two separate databases, and zero direct service-to-service HTTP calls for
any of it — actual event-driven ownership of data, applied consistently
across every write path that needed it, not demonstrated once and left at
that.

Google OAuth gets its own edge case handled properly, too: a first-time
Google sign-in has no username yet, so `auth-service` stashes the pending
profile in a `TempGoogleUser` and redirects to a "complete profile" step
instead of half-creating an account.

### email-service: a Priority Queue Built on Kafka Partitions

This is the piece I'd point to first if someone asked what the most
genuinely clever engineering in this project was. Kafka doesn't give you a
priority queue — partitions are just parallel logs. So the design uses
partition number _as_ priority: low-numbered partitions get drained first,
and if a higher-priority message shows up while a lower-priority partition
is mid-processing, the loop **preempts** back to it immediately:

```js
const messagesChunk = partitionMessages.splice(0, rateLimit);
// ...process this chunk...

const newMessagesIndex = newPriorityMessagesPartitionIndex(partitionIndex);
if (newMessagesIndex >= 0) {
  partitionIndex = newMessagesIndex - 1; // jump back to the higher-priority partition
  break;
}
```

That sits behind a rate limiter (a budget that decrements per message sent
and resets on an interval, so a burst of sign-ups can't get an email
provider's account flagged for abuse), and offsets are committed **only
after** the mail actually sends —

```js
await sendMail({ subject, text, to: parsedMessage.data.to, html });
await consumer.commitOffsets([{ offset: ..., partition: partitionIndex, topic: TOPIC_NAME }]);
```

— so a crash mid-send means that message gets redelivered on restart
instead of silently lost. Add an idempotent topic bootstrap (checks if the
topic exists before creating it, with the partition count baked in) and a
template registry keyed by message `type` (`auth/verification`,
`auth/update-email-verification`, `welcome`, each a `{ subject, text,
html }` function), and this one service alone is a genuinely complete,
correctly-reasoned piece of infrastructure — priority handling, backpressure,
and at-least-once delivery, not just "consume a topic and call sendMail."

The design work went further than boxes and arrows, too — this is the
message-level flow I planned for the social-graph slice (User, Notification,
Follow), specifying exactly what gets published to Kafka and when: a
follow/unfollow pushes a message, a notification service listens and pushes
back out, follower/following counts get batch-updated, and the write lands
in MongoDB:

![A detailed Kafka message-flow design for User, Notification, and Follow — specific event names ("Push the follow up/down msg," "Batch update the followers/following totalcount") down to which service writes to MongoDB](/dev-sync/dev-sync-kafka-flow.png)

That level of detail existed for more of the system than the five services
that ended up running — this is what "paused mid-build" actually looks
like: real design work for pieces that didn't get their own repo yet.

Five separate repos, each with its own Docker build, is exactly the kind of
setup that's a pain for anyone but the original author to run locally.

## The Part I'm Most Proud Of: Making Five Repos Feel Like One

A microservices project split across five separate GitHub repos is a pain
to onboard into — clone five things, get the branching right, build five
Docker images, wire up Kafka/Redis/Mongo yourself. I didn't want that to be
the cost of contributing, so I built a small orchestrator repo
(`dev-sync-server`) around two commands.

For a new contributor, `npm run dev` forks each of the five service repos
onto their own GitHub account, clones them into `services/`, builds each
one's Docker image, and brings the whole stack up with one
`docker compose` call:

```js
async function buildService(service) {
  const repoUrl =
    GITHUB_USERNAME !== OWNER
      ? await forkRepository(service) // fork it onto the contributor's own GitHub
      : service.repo;

  await cloneOrUpdateRepository(service, repoUrl);
  await buildDockerImage(service); // npm install + docker build -f Dockerfile.dev
}

await Promise.all(services.map(buildService));
await execAsync(`docker compose -f docker-compose.dev.yml up -d`);
```

And `npm run sync` keeps a contributor's forks current: it adds an
`upstream` remote pointing back to my original repos if one doesn't exist,
fetches and merges upstream's latest changes into each local service
branch, and pushes the result back to their fork — five repos, kept in sync
with one command, which is where the project's name actually comes from.

```js
await git.addRemote('upstream', `https://github.com/${OWNER}/${service.name}.git`);
await git.fetch('upstream', branch);
await git.mergeFromTo(`upstream/${branch}`, branch);
await git.push('origin', branch);
```

Clone one repo, run `npm run dev`, and the entire five-service stack —
forked, built, containerized — is running locally. That tooling is six
commits and a few hundred lines; if email-service's priority queue is the
cleverest single piece of this project, this is the most practically
useful one.

## Why It's Paused, Not Abandoned

Client work came in and had to take priority — Bicar, then Kathika, then
Server Template — and Dev Sync never got the sustained block of time back
that a ~20-service platform needs to go from "three services work end to
end" to "finished." That's a real, unresolved gap, not a twist ending: this
is an honest unfinished project, not a disguised finished one.

## What I Learned

This is the project where microservices stopped being a term I'd read about
and became something I'd actually built: services that own their own data,
talk to each other over Kafka instead of direct calls, get containerized
independently, and need real tooling to make local development tractable
across repo boundaries. It's also where I got serious about UI design as
its own discipline — a real design system, not just picking colors as I
went — before writing a single component. Both of those show up directly
in every client project after this one.
