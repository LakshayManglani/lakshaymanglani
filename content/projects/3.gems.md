variety, shape, clarity, weight, and price, real checkout. I'm building

## Three Services, One Job Each

Everything runs self-hosted on my own hardware — a Dell Inspiron 3471,
8GB RAM, 256GB SSD. Not high-end, which is part of the point: the
architecture had to earn its speed, not borrow it from bigger iron.

- **Nuxt frontend** — the storefront itself. Every request the browser
  makes goes to this one origin.
- **Rust query server** — the only thing the storefront actually talks to.
  Its entire job is answering "show me these products, filtered this way,"
  as fast as possible.
- **Fastify server** — order flow and the rest of the business logic.
  Built on my own `server-template`, and deliberately kept separate from
  the storefront for now — it isn't wired up to the live site yet.

![Architecture — the Nuxt frontend proxies catalog reads to the Rust query server; the Fastify server handles orders separately and isn't wired to the storefront yet; only Fastify hits Postgres on every request, the Rust server refreshes from it in the background](/gems/gems_architecture.png)

The Nuxt server is the only thing the browser ever talks to — it proxies
catalog requests through to the Rust service internally. That means the
client never needs to know how many backend services exist or what any of
them are built in; the storefront could switch which service answers a
given route without any client-side change.

## Why a Second Server, When I Already Had Fastify

I already had a production-shaped Fastify template. The obvious move was
to use it for the catalog too. I didn't, on purpose.

Gem inventory doesn't change every millisecond — prices and stock update
occasionally, not constantly. But the single most-hit action on the whole
site is "fetch products and show them," over and over, with different
filters each time. Optimizing that one path mattered more than anything
else in the system. A general-purpose API server hitting Postgres on every
request is the correct default — until the read pattern is this lopsided,
at which point paying a DB round-trip for every single page view is
avoidable, self-inflicted latency.

So I scoped a second service to do exactly one thing: serve the product
catalog from memory, refresh it from the database in the background, and
never make a request wait on a DB call. Rust and Axum, purpose-built, not
a rewrite of the Fastify server in a different language.

The refresh strategy is adaptive rather than fixed: it polls the database
on a slow interval when nothing's happening, and tightens back down to a
fast interval automatically the moment real traffic shows up — so a
freshly-changed product shows up within seconds under actual load, not
after some fixed worst-case delay chosen up front. It's an eventual-
consistency trade-off, deliberately: this catalog doesn't need
read-your-writes guarantees, it needs to be fast almost all the time and
correct within a few seconds the rest of the time.

## The Numbers

I didn't just benchmark the Rust service in isolation — I load-tested the
same endpoint served the old way (Fastify querying Postgres directly) to
see what the decision above actually bought me. Same tool, same load
shape, same machine: `autocannon`, 100 concurrent connections, 30 seconds.

**Rust query server (serves from the in-memory cache):**

|         | 2.5% | 50% | 97.5% | 99%  | Avg    | Max  |
| ------- | ---- | --- | ----- | ---- | ------ | ---- |
| Latency | 1ms  | 6ms | 11ms  | 13ms | 6.04ms | 48ms |

15,296 requests/sec average, 459k requests over 30 seconds, 9.09GB
transferred.

**Fastify hitting Postgres directly, same endpoint, same load:**

|         | 2.5%   | 50%    | 97.5%  | 99%    | Avg       | Max    |
| ------- | ------ | ------ | ------ | ------ | --------- | ------ |
| Latency | 3826ms | 3967ms | 5233ms | 5391ms | 4070.86ms | 5770ms |

23.34 requests/sec average, 800 requests over 30 seconds.

That's roughly **650x more throughput and 650x lower latency** — 6ms vs.
~4 seconds at the median. To be precise about what's actually being
compared: this isn't "Fastify is slow" (the
[server-template case study](/projects/server-template) is the strongest
engineering I've shipped, and it's Fastify). It's that a full database
query on every single request doesn't hold up once 100 clients are asking
for the same thing at once — the query server exists specifically to take
that query out of the request path entirely.

One honest caveat on the Fastify number: the production route actually
has a rate limiter in front of it, capped around 100 requests, exactly to
stop the database from getting hammered like this. I raised that limit
for this one test to actually see what was underneath it — the first run
came back as 195,005 non-2xx responses (the limiter doing its job), which
told me nothing about the database path itself. The 4-second number above
is what the DB round-trip costs once you remove the guardrail, which is
the honest way to measure the thing the Rust service was built to avoid.

## The Frontend: `swr` Instead of Full SSR

The catalog page doesn't need to re-render on the server for every
request either — the same "it doesn't change every millisecond" logic
applies to the page itself, not just the API behind it:

```ts
routeRules: {
  "/": {
    swr: 5,
  },
},
```

The homepage is served as a static response and revalidated in the
background every 5 seconds, instead of doing full SSR work per request.
Measured in the browser on the live site: the document itself lands in
21-28ms on the network tab, and LCP comes in at 0.75s. Total main-thread
work across a full trace — scripting, rendering, painting — is under 6
seconds cumulative for the whole session, not per page.
